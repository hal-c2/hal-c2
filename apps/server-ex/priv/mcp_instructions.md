## HAL-C2 orchestration

The `hal-c2` MCP server provides app-owned orchestration. Treat these concepts distinctly:

- Hand work to another agent with the `hal-c2` tools. HAL-C2 only shows, cancels and wakes work started through them.
- `delegate_task` starts child work owned by this thread: research, review, a parallel implementation slice, and any worker that will itself fan out. It shows in the Agents panel, can be cancelled with `task_cancel`, and wakes this thread when it is done. After starting async children, say what you started and end your turn. Do not poll, sleep, or spawn watchers; each child's result arrives as a new message here. Use `task_status` only when you need a result mid-turn. Choose a provider and model with `orchestrator_capabilities` (pass `providerInstanceId` for one provider's full model list). Retain each returned `taskId`; the `childThreadId` is backing storage, not an ordinary thread.
- Your provider's own subagent tool (Task, Agent) is only for quick read-only lookups that finish within the current turn. Never use it for work that edits files, runs long, or fans out.
- A worker that needs its own worktree, including an implementation worker or a PR, is still a `delegate_task`: pass its `workspace` option (omitted means your worktree; `{"type":"worktree"}` makes a new one from your branch; `{"type":"existing_worktree","worktreePath":"..."}` uses an existing one). Never run `git worktree add` yourself or tell a worker to: the thread binding goes stale.
- `hal_c2_thread_launch` and `create_threads` create ordinary top-level HAL-C2 conversations in the sidebar, not workers. Use them only when the user explicitly asks for separate/new/top-level threads or conversations; never because the user said "subagent" or asked for parallel work. Their results are not delivered back to you, so follow them with `hal_c2_thread_read`, and use `hal_c2_thread_wait` only when this turn cannot finish without it.
- `schedule_task` creates persistent recurring work in the app scheduler. Pass `schedule` as a structured object, never as JSON text: `{"type":"interval","everyMs":3600000}` for an interval, or `{"type":"fixed_time","timeOfDay":"09:00","weekdays":[1,2,3,4,5]}` for a wall-clock schedule. By default runs return to the current thread; set `bindToCurrentThread=false` only when the user wants a fresh thread for every run. After scheduling, report the returned cadence and next run time.

### A declined approval is the user's answer

When the user declines an approval, that is a decision, not a transient failure. Do not ask again for the same action, and do not reach the same end another way: no rephrased command, other tool, other path, other network host, or environment-variable workaround. Stop that line of work, say in one short message what you needed and why, and wait for the user. Never fire a burst of approval requests: ask for one action at a time, and treat any decline as a reason to stop and ask rather than to try the next variant. If a step needs network access or installs (package registries, toolchain downloads) the task did not call for, ask first instead of attempting it.

### Choose the workspace before starting a new thread

When the user asks for a separate top-level thread in its own worktree (a PR stack, say), use `hal_c2_thread_launch` with an explicit `workspaceStrategy`. It creates or selects the workspace, binds the new thread to it, and prepares it before the agent starts. Put the task in `message`, not `prompt`:

- New worktree: `{"title":"UI cleanup","workspaceStrategy":{"type":"worktree","baseRef":"feature/base","branch":"feature/ui-cleanup","startFromOrigin":false},"message":"Implement the cleanup and open a PR against feature/base."}`
- Existing worktree: `{"title":"Continue cleanup","workspaceStrategy":{"type":"existing_worktree","worktreePath":"/absolute/path/to/worktree","branch":"feature/ui-cleanup"},"message":"Continue the cleanup."}`
- Project's main checkout: `workspaceStrategy:{"type":"root"}`. Omitting workspaceStrategy also selects root; it does not inherit the caller's worktree.

For stacked work, set `baseRef` to the intended parent branch and `startFromOrigin:false` to use its local commits. Use `startFromOrigin:true` when you intend to fetch and start from origin. Uncommitted edits are not copied. Use `hal_c2_worktree_list` to discover existing checkout paths. Project, model selection, and modes inherit unless supplied; launch requires a full-access/default caller.

`hal_c2_thread_launch` is the single-thread launch tool. Use `create_threads` only for a batch of threads intentionally sharing the caller's checkout: it always inherits the caller's project, branch, and worktree and has no workspace override. Never create a worktree with `git worktree add`, or ask an agent to, or `cd` elsewhere: that does not update HAL-C2's thread binding, which goes stale. Select the workspace in the launch call (or `delegate_task`'s `workspace`) instead. `hal_c2_worktree_handoff` moves the calling thread, not another thread, and cannot move a thread already attached to a worktree.

`hal_c2_thread_launch` has no idempotency key. Retain its returned threadId and inspect it with `hal_c2_thread_read` / `hal_c2_thread_wait`; preparation can still be running after acceptance. If a launch fails or its response is lost, inspect `hal_c2_thread_list` before retrying, since a thread may already exist.

Tool names may include a harness-normalized MCP prefix, such as `mcp__hal_c2__delegate_task`; the semantics are the same. Some harnesses attach optional MCP servers lazily: if an initial tool-catalog scan does not show HAL-C2 tools, do not conclude that cross-provider delegation is unavailable. Make one bounded direct attempt using the known HAL-C2 tool name on the next tool step. In Codex code mode, for example, call `tools.mcp__hal_c2__orchestrator_capabilities({})` before reporting that the capability is absent. Keep polling/wait loops bounded, do not duplicate active work, and use stable `clientRequestId` values when retrying tools that accept them.
